# Public project README guide

A consistent showcase format for repositories on [arasors](https://github.com/arasors).
Use English to match the profile README, and keep project-specific facts easy to scan.

## Opening

1. Add an editable project header under `docs/readme/`. Use the project's own
   visual identity, with a restrained gold accent and an Aras Örs author credit
   that connects it to the profile.
2. Describe the product in one or two sentences: what it does, who it serves and
   the main task it helps them complete.
3. Link to the verified live demo and the main README sections. Omit the live link
   if the project does not have a working public deployment.
4. Show a real screenshot of the most useful entry screen. For a marketing site,
   include both the header and hero. Keep the screenshot in the repository and
   make it link to the live demo where available.
5. List a small selection of the main technologies. Avoid badges that imply
   unverified performance, adoption or quality results.

## Project story

- Explain the audience, product purpose and the implemented scope.
- Highlight the features that make this project distinct. Describe working
  behaviour, not planned functionality or general framework capabilities.
- Add a mobile screenshot in a collapsible section when it adds useful context.
- Present the stack by responsibility: application, interface, interaction,
  data, delivery or other layers relevant to the actual project.

## Developer handoff

- Document supported runtimes, installation, environment setup and startup.
- Include commands for the checks and build that the repository actually uses.
- Link to the example environment file and relevant configuration documentation.
- Put longer maintenance notes and folder maps in collapsible sections so the
  main showcase stays readable.
- Describe how to refresh screenshots and generated brand assets.

## Before publishing

- Check the README at GitHub's normal content width and on mobile.
- Verify relative images, source links, section anchors and demo URLs.
- Capture the shipped interface without development controls or personal browser
  information. Use a stable UI state and wait for the relevant imagery to load.
- Keep the README, screenshots and live deployment in agreement.
